# Valthera — продукт, архитектура и план развития

## Цель

Личный финансовый менеджер для ручного учёта доходов и расходов. Первая версия должна позволять ежедневно записывать операции, исправлять ошибки, видеть остатки денег и понимать расходы за месяц.

Дополнительная цель — инженерный проект для портфолио с понятной архитектурой, проверяемой корректностью, безопасностью и воспроизводимым запуском. Единого «стандарта бигтехов» не предполагаем: качество оцениваем по конкретным требованиям и результатам проверок. Продвинутые технологии внедряем по этапам с описанием задачи, гарантий и компромиссов. Описанное ниже — целевой план, а не перечень уже реализованных возможностей.

Основные технологии:

- React + TypeScript — веб-клиент, первый интерфейс для разработки и проверки продукта.
- Go — REST API.
- PostgreSQL — хранение данных.
- Flutter — мобильный клиент после готовности основного API и веб-сценариев. Использует тот же API; не блокирует выпуск веб-MVP.

## Разделение работы

- Пользователь самостоятельно реализует Go-бэкенд и изучает язык в процессе.
- Ассистент помогает с бэкендом поэтапно: объясняет задачу, предлагает небольшие примеры, разбирает вопросы и проверяет написанный код. Не реализует весь сервер вместо пользователя без отдельной просьбы.
- Ассистент реализует React-сайт: визуальный дизайн, адаптивные экраны, формы и интеграцию с API.
- До готовности сервера веб-клиент может работать с демонстрационными данными через заменяемый слой доступа к данным. Деморежим явно обозначается; это не хранение реальных финансов.
- Контракт API согласовываем перед подключением соответствующего экрана. Изменения согласованного поведения отражаем в этом документе.
- Бэкенд развивается в отдельном публичном репозитории `github.com/LegionAlpha/valthera-backend`. Основная ветка — `main`; при необходимости используем предметные имена вроде `feature/accounts` и `fix/transfer-validation`. Без AI-префиксов, служебных AI-файлов и пометок в коммитах.
- Фронтенд больше не публикуем и не отправляем в удалённые репозитории без нового явного поручения пользователя. План доступен в корневом design.md и в design.md репозитория бэкенда; при изменении общего контракта обновляем соответствующие разделы обеих копий, не затирая другие изменения.

## Границы первой версии

- Ручной ввод операций, без банковских интеграций.
- Одна валюта во всём профиле. Стартовое допущение — RUB, суммы с двумя десятичными знаками. Конвертации нет.
- Личный учёт без совместного доступа и семейных бюджетов.
- Работа с сервером требует подключения к сети; офлайн-режим и синхронизацию откладываем.
- Локальную разработку начинаем с одного тестового пользователя без экрана входа. Перед доступом через интернет обязательны авторизация и изоляция данных пользователей.
- Переводы между счетами входят в завершённый MVP, но реализуются после обычных доходов и расходов.
- Идемпотентное создание финансовых операций, защита от конкурентных изменений, тесты и CI входят в качество MVP. gRPC, брокер и Redis добавляются после рабочего финансового ядра и не блокируют первый локальный сценарий.

## Функциональность

### Счета

- Создание счёта с названием и начальным балансом: например, «Основная карта» или «Наличные».
- Просмотр списка счетов, баланса каждого счёта и общей суммы денег.
- Изменение названия и начального баланса. Изменение начального баланса пересчитывает текущий остаток.
- Архивация счёта вместо удаления его истории. Архивный счёт виден в истории, но недоступен для новых операций.
- Архивация разрешена только при нулевом текущем балансе; счёт можно восстановить.
- Пока счёт в архиве, его начальный баланс и связанные с ним операции, включая переводы, нельзя изменить или удалить. Сервер отвечает `409 account_archived`. Чтобы исправить историю, счёт сначала восстанавливают.
- Названия счетов могут повторяться; идентификатор — `id`. Название нормализуется: обрезаются пробелы по краям, затем применяется Unicode NFC.
- Отрицательный баланс допустим; проверку доступных средств не вводим.

### Категории

- Готовые категории расходов: продукты, кафе, транспорт, жильё, здоровье, покупки, развлечения, прочее.
- Готовые категории доходов: зарплата, подарки, прочее.
- Категория принадлежит типу операции: доход или расход.
- У категории есть стабильный `code` (например, `groceries`) и `sort_order`; отображаемое название не служит идентификатором. Готовые категории создаются миграцией и общие для всех пользователей.
- Создание, редактирование и удаление пользовательских категорий откладываем.

### Доходы и расходы

- Создание операции: тип, положительная сумма, счёт, категория, дата и необязательный комментарий.
- Дата по умолчанию — сегодня по локальной дате пользователя. Будущие даты в MVP не принимаются; запланированные платежи появятся отдельно.
- Сервер не знает часовой пояс пользователя и работает только с календарными датами и UTC. Локальную дату вычисляет фронтенд и передаёт её готовой; он же запрещает выбор будущей даты. Сервер отклоняет дату позже текущей даты UTC + 1 день (допуск на часовые пояса до UTC+14) и раньше `2000-01-01`.
- Редактирование всех полей и удаление операции с подтверждением.
- После любого изменения обновляются история, балансы и сводка.
- Комментарий — до 500 символов, название счёта — от 1 до 80 символов после удаления пробелов по краям.
- История сортируется по дате операции от новых к старым, при одинаковой дате — по времени создания, затем по `id`. Порядок полностью детерминирован, поэтому записи не повторяются и не теряются между страницами.
- Фильтры: месяц, счёт, тип операции и категория. Фильтры совместимы друг с другом; есть сброс.
- Постраничная загрузка истории: по 50 записей.

### Переводы

- Перевод положительной суммы между двумя разными активными счетами в общей валюте.
- Поля: счёт отправления, счёт получения, сумма, дата, необязательный комментарий.
- Перевод отображается в истории одной записью с обоими счетами.
- Перевод уменьшает один баланс и увеличивает другой; общая сумма денег не меняется.
- Переводы не входят в доходы, расходы и статистику категорий.
- Перевод можно изменить или удалить целиком. Частичное сохранение недопустимо.
- Комиссии и обмен валют не поддерживаются; комиссию при необходимости пользователь записывает отдельным расходом.

### Сводка

- Общий текущий баланс и текущие балансы счетов, независимо от выбранного месяца.
- Доходы, расходы и разница доходов и расходов за выбранный календарный месяц.
- Распределение расходов по категориям: сумма, доля и простая диаграмма. Сервер возвращает точные суммы в минимальных единицах; доли округляет до десятых процента методом наибольшего остатка, чтобы их сумма была ровно 100%.
- Последние пять операций и переход к полной истории.
- Переключение месяца. Месяц `YYYY-MM` обязателен в запросе: текущий месяц определяет фронтенд по локальной дате. При отсутствии операций показываем понятное пустое состояние, без выдуманных показателей.
- Начальные балансы не считаются доходами и не участвуют в месячной статистике.

### Регистрация, вход и защита данных

- Учётная запись пользователя (`users`) отделена от финансового счёта (`accounts`). Реализуем регистрацию по email и паролю, вход, выход из текущей сессии и получение текущего пользователя. Первый этап проверяем локально; публичную регистрацию включаем только после подтверждения email, восстановления пароля и защиты от злоупотреблений.
- Регистрация управляется явной настройкой и по умолчанию выключена. До готовности почтовых сценариев включённая регистрация допускается только в локальном режиме; отсутствие настройки не должно открывать публичную регистрацию.
- Email: `strings.TrimSpace`, затем проверка поддерживаемого ASCII-адреса и приведение всего адреса к нижнему регистру. Это продуктовое правило нечувствительности к регистру, включая local part. Максимум 254 байта; display name, комментарии, quoted local part и Unicode-адреса на первом этапе не поддерживаем. Точки и `+suffix` не удаляем. Нормализованный email уникален в PostgreSQL, в том числе при конкурентной регистрации.
- Пароль: 8–128 Unicode code points, корректный UTF-8 без U+0000; пробелы разрешены. Не применяем TrimSpace, NFC, смену регистра или тихое усечение. Храним Argon2id в формате PHC с индивидуальной случайной солью и параметрами; параметры выбираем по OWASP и измерениям перед реализацией. Ограничиваем размер HTTP-тела и число одновременно выполняемых вычислений хеша.
- Локальный контракт регистрации: `201` с публичными полями пользователя, без автоматического входа; повтор нормализованного email — `409 registration_conflict`. Такой ответ позволяет определить занятость email: до публичной регистрации пересматриваем его вместе с почтовым подтверждением и защитой от перебора. Хеш пароля никогда не возвращаем клиенту.
- Вход: `200` и новая серверная сессия; неизвестный email, неверный пароль и пользователь без учётных данных дают одинаковые `401 invalid_credentials`. Для отсутствующего пользователя выполняем проверку заранее подготовленного фиктивного хеша с теми же параметрами. Лимиты применяем до дорогого хеширования.
- Сервер получает 32 случайных байта токена через `crypto/rand`; браузеру передаёт base64url без padding в HttpOnly-cookie, в базе хранит только SHA-256 исходных 32 байт (`BYTEA`, ровно 32 байта, UNIQUE). UUID сессии — внутренний идентификатор строки, не секрет и не токен доступа. На каждом входе создаём новый токен; несколько сессий одного пользователя допустимы.
- Для HTTPS используем cookie `__Host-valthera_session`: Secure, HttpOnly, SameSite=Lax, Path=/, без Domain. Для явно включённой локальной разработки по HTTP — отдельное имя `valthera_session`, без Secure, только при локальном доступе. Токен не передаём в JSON, URL, логах или localStorage.
- Абсолютный срок сессии — 30 суток (720 часов); неактивность — 7 суток (168 часов). Доступ разрешён, когда revoked_at IS NULL, now < expires_at и now < last_seen_at + 168 часов. expires_at задаётся при входе и не продлевается. Middleware атомарно проверяет сроки и отзыв и обновляет last_seen_at только для действующей сессии; истёкшую сессию нельзя оживить обновлением даты. Используем согласованное серверное время; клиентские даты не принимаем.
- Logout отзывает текущую сессию и очищает cookie с теми же Path/Domain. После проверки Origin возвращает `204`, в том числе при отсутствующем или уже недействительном токене. Остальные сессии остаются действующими. Запрос, уже прошедший проверку до отзыва, может завершиться; следующий запрос с отозванным токеном отклоняется.
- `/auth/me` возвращает `id`, `email`, `created_at`; без действующей сессии — `401 unauthorized`. Cookie Max-Age не превышает оставшийся абсолютный срок; сроки доступа всегда проверяет сервер. Просроченные/отозванные строки можно чистить фоново, но безопасность не зависит от очистки.
- Все финансовые маршруты получают владельца из проверенной сессии. После подключения middleware удаляем обход через DEV_USER_ID. Проверяем изоляцию минимум двух пользователей; пользователь без email/password_hash не может войти и не должен получить сессию.
- CSRF: SameSite=Lax и обязательный Origin для всех изменяющих запросов, включая register/login/logout. Сравниваем схему, хост и эффективный порт с настроенным списком. Отсутствующий, null, некорректный или чужой Origin — `403 forbidden_origin`; Referer не служит fallback. CLI явно передаёт разрешённый Origin. Это не замена авторизации; GET не требует Origin, но защищён сессией.
- Вход: максимум 5 неудачных попыток за 15 минут отдельно на нормализованный email и на IP; превышение — `429`. Регистрация: максимум 5 попыток за час на IP на локальном этапе; перед публичным запуском пересматриваем значения. Доверяем forwarded IP только от настроенных reverse proxy. Начальный лимитер в памяти допустим только для одного процесса, с ограниченной памятью и очисткой; при масштабировании потребуется общий лимитер.
- Подтверждение email и восстановление пароля — следующий обязательный этап перед публичной регистрацией; их таблицы и API проектируем отдельно. OAuth и MFA откладываем.

### Миграция учётных данных и сессий

- После `00002_create_transactions.sql` добавляем `00003_add_user_credentials_and_sessions.sql`; применённые миграции не редактируем.
- В users добавляем nullable email и password_hash. CHECK разрешает только оба NULL (старый пользователь без входа) либо оба заполнены. Email хранится нормализованным, UNIQUE допускает несколько NULL; password_hash — непустая PHC-строка. Currency пока не добавляем: действующее правило продукта — одна общая RUB.
- Существующие пользователи, их UUID, счета и операции сохраняются. Не назначаем общие пароли, фиктивные email или учётные данные из миграции. Регистрация всегда создаёт нового пользователя с обоими полями; привязка старого пользователя к данным входа — отдельная явная административная операция с теми же правилами и хешированием.
- sessions: id UUID, user_id UUID FK, token_hash BYTEA UNIQUE, created_at, last_seen_at, expires_at, revoked_at. Проверяем длину хеша и порядок временных меток; реальные сроки действия и наличие учётных данных проверяются прикладным кодом. FK при удалении пользователя каскадно удаляет сессии; финансовые FK по-прежнему запрещают случайное удаление владельца данных.
- Индексы sessions(user_id) и sessions(expires_at) нужны для операций по владельцу и очистки по абсолютному сроку. UNIQUE(token_hash) уже создаёт индекс поиска токена.
- Down сначала удаляет sessions, затем ограничения и поля учётных данных users. Счета и операции сохраняются, но пароли/email и сессии теряются; откат используем только на одноразовой тестовой базе или после отдельного решения о восстановлении данных.

## React-сайт

### Визуальное направление

Спокойный современный финансовый интерфейс: светлый фон, тёмная типографика, изумрудный акцент, аккуратные карточки и достаточно свободного пространства. Суммы должны легко читаться и сравниваться. Цвет дохода или расхода дополняется подписью и знаком, чтобы смысл не зависел от цвета.

На широком экране — боковая навигация и просторная рабочая область. На телефоне — компактная навигация и формы на всю ширину. Интерфейс на русском языке; суммы и даты форматируются привычным образом. Тёмную тему откладываем.

### Экраны

1. **Обзор**: общий баланс, карточки доходов и расходов за месяц, расходы по категориям, последние операции, кнопка добавления.
2. **Операции**: история, фильтры, пагинация, создание, редактирование и удаление. На десктопе — таблица, на узком экране — удобный список.
3. **Счета**: карточки счетов с остатками, создание и редактирование, просмотр и восстановление архивных счетов.
4. **Вход и регистрация**: email, пароль, ошибки валидации и входа; выход из текущей сессии. Регистрация показывается только когда разрешена сервером.

Доход, расход и перевод создаются через общую точку входа с выбором типа. Формы показывают ошибки рядом с полями и сохраняют введённые значения при сбое запроса. Во время отправки повторное нажатие блокируется. После успешного сохранения интерфейс обновляется без ручной перезагрузки.

Обязательные состояния: загрузка, пустой список, отсутствие результатов по фильтрам, ошибка сервера с повтором запроса и истёкшая сессия. Поддерживаем клавиатурную навигацию, видимый фокус, подписи полей и читаемый контраст.

## Данные и правила расчёта

Минимальные сущности:

| Сущность | Основные поля |
| --- | --- |
| User | id, email, password_hash, created_at |
| Session | id, user_id, token_hash, created_at, last_seen_at, expires_at, revoked_at |
| Account | id, user_id, name, initial_balance_minor, archived_at, version, created_at, updated_at |
| Category | id, code, name, type, sort_order |
| Transaction | id, user_id, type, account_id, destination_account_id, category_id, amount_minor, date, comment, version, created_at, updated_at |
| IdempotencyKey | user_id, operation, key, request_fingerprint, resource_id, response_status, response_body, created_at |

`type` принимает `income`, `expense` или `transfer`. Для обычной операции обязательны `account_id` и `category_id`, а `destination_account_id` отсутствует. Для перевода обязательны оба разных счёта, а категория отсутствует.

- Деньги храним целым числом минимальных единиц валюты: `125050` означает `1250,50`. В Go — `int64`, в PostgreSQL — `BIGINT`. `float64` для денег не используем.
- API передаёт денежные значения целыми JSON-числами. Суммы и вычисленные итоги ограничиваем безопасным целочисленным диапазоном JavaScript; переполнение проверяем на сервере.
- Ввод суммы с десятичным разделителем преобразуется в минимальные единицы без округления через двоичную арифметику. Более двух знаков после разделителя — ошибка ввода.
- `date` — календарная дата `YYYY-MM-DD`, без часового пояса. Технические метки создания и изменения — UTC; в локальное время их переводит клиент.
- Максимальная сумма одной операции и начального баланса по модулю — `10^13` минимальных единиц (100 млрд в валюте). Предел закреплён `CHECK` в схеме; итоги считаются в `int64` с проверкой переполнения и не выходят за `2^53 − 1`.
- Операции удаляются физически. Журнал изменений (audit log) откладываем на после MVP.
- Баланс = начальный остаток + доходы − расходы + входящие переводы − исходящие переводы.
- Текущий баланс вычисляем из записей; отдельный изменяемый итог в таблице счетов пока не храним.
- Сводку и балансы считает сервер, чтобы React и Flutter получали одинаковые результаты.
- Проверки полей выполняются и в клиенте для удобства, и в сервере для корректности.

## Предварительный REST API

Все маршруты таблицы, кроме `/health` и `/ready`, включая `/auth/*`, находятся под префиксом `/api/v1`. Точные DTO фиксируем при реализации соответствующего этапа в OpenAPI. TypeScript-типы веб-клиента генерируются из OpenAPI, а не пишутся вручную.

| Метод и путь | Назначение |
| --- | --- |
| GET /health | Liveness: процесс обрабатывает HTTP, без обращения к базе |
| GET /ready | Readiness: готовность принимать запросы, включая доступность PostgreSQL |
| GET /accounts | Список счетов с балансами; параметр для включения архивных |
| POST /accounts | Создание счёта |
| PATCH /accounts/{id} | Изменение названия или начального баланса |
| POST /accounts/{id}/archive | Архивация; `409 account_balance_not_zero` при ненулевом балансе |
| POST /accounts/{id}/restore | Восстановление из архива |
| GET /categories | Готовые категории; необязательный фильтр типа |
| GET /transactions | История: month, account_id, type, category_id, limit, offset |
| POST /transactions | Создание дохода, расхода или перевода |
| PATCH /transactions/{id} | Редактирование операции без смены её типа |
| DELETE /transactions/{id} | Удаление операции |
| GET /summary?month=YYYY-MM | Общий баланс, итоги месяца и расходы по категориям; `month` обязателен |
| POST /auth/register | Регистрация по email и паролю, когда разрешена настройкой |
| POST /auth/login | Вход и создание сессии |
| POST /auth/logout | Выход |
| GET /auth/me | Текущий пользователь |

Фильтр истории по счёту включает переводы, где счёт является отправителем или получателем. Месяц в истории можно не передавать для просмотра всех дат. Для пагинации ответ содержит `items`, `total`, `limit`, `offset`; максимальный `limit` — 100.

Ошибки имеют единый формат: `error.code`, `error.message`, при необходимости `error.fields`. Используем осмысленные HTTP-статусы: 400 для неверных данных, 401 для отсутствия сессии, 403 для отклонённого `Origin`, 404 для отсутствующей или чужой записи, 409 для конфликта состояния, 413 для слишком большого тела, 428 для отсутствующей версии, 429 для превышения лимита, 500 для внутренней ошибки. В ответах не раскрываем SQL и внутренние детали сервера.

Версия записи передаётся в теле `PATCH`-запроса в поле `version`; отсутствие поля даёт `428 version_required`, несовпадение — `409 version_conflict`.

Каталог машинных `error.code` ведём в OpenAPI. Стартовый набор: `registration_conflict`, `registration_disabled`, `invalid_credentials`, `validation_failed`, `unauthorized`, `forbidden_origin`, `not_found`, `version_required`, `version_conflict`, `account_archived`, `account_balance_not_zero`, `category_type_mismatch`, `same_account_transfer`, `amount_out_of_range`, `date_out_of_range`, `idempotency_key_missing`, `idempotency_key_reused`, `idempotency_in_progress`, `payload_too_large`, `rate_limited`, `internal`.

## Устройство бэкенда

Начинаем с модульного монолита: один Go-сервис и одна PostgreSQL-база. Используем стандартный `net/http`, `pgx/pgxpool` и явный SQL. Бизнес-правила не зависят от транспорта, драйвера базы, брокера или кэша. Дальнейшее выделение процессов опирается на реальные границы задач, описанные в разделе развития после MVP.

Схема базы изменяется версионированными SQL-миграциями. Настройки подключения и секреты приходят из окружения. Логи не содержат паролей, cookie и содержимого личных комментариев.

### Границы ответственности

- HTTP-слой разбирает запрос, ограничивает размер тела, проверяет формат, получает пользователя из доверенного контекста и преобразует результат в ответ. В нём нет SQL и правил расчёта денег.
- Прикладные сервисы выполняют сценарии: создать счёт, записать расход, перевести деньги. Здесь проверяются бизнес-правила, авторизация на уровне ресурса и условия выполнения операции.
- Пакеты предметной области содержат типы, ошибки и правила, не зависящие от HTTP и PostgreSQL.
- PostgreSQL-адаптер реализует запросы и атомарные операции хранения. Границы транзакций определяются сценарием; несколько связанных записей нельзя сохранять независимыми вызовами без общей транзакции.
- Зависимости передаются через конструкторы. Глобальных подключений и контейнера зависимостей не используем. Узкие интерфейсы объявляет потребитель, когда они нужны для границы или теста; интерфейс для каждой структуры не создаём.
- `cmd/api` собирает зависимости, управляет жизненным циклом и запускает сервер. Пакеты `utils`, универсальные CRUD-репозитории и лишние слои без своей ответственности не вводим.

### Корректность финансовых данных и конкурентные запросы

- PostgreSQL — источник истины. Деньги не храним в Redis как единственный источник данных.
- Суммы, типы операций, разные счета перевода и обязательность полей защищены не только Go-валидацией, но и ограничениями SQL (`CHECK`, `NOT NULL`, внешние ключи). Принадлежность связанных счетов одному владельцу также защищаем схемой, где это возможно.
- Перевод представлен одной финансовой операцией; изменение обоих вычисляемых балансов атомарно связано с её сохранением. Нельзя независимо сохранить «списание» и «зачисление».
- Изменения счетов и операций сериализуем по затронутым счетам внутри SQL-транзакции: блокировка строк счетов в стабильном порядке идентификаторов, затем проверка актуального состояния. Все пути записи соблюдают тот же протокол, включая смену счёта операции, её удаление и изменение начального остатка.
- Проверка нулевого баланса и архивация выполняются в одной транзакции под блокировкой. Новая операция не может пройти между проверкой и архивацией.
- Для редактирования добавляем `version`: клиент передаёт прочитанную версию, SQL обновляет запись только при совпадении. Устаревшее изменение получает `409`, а не молча перезаписывает чужую правку. Проверка версии дополняет блокировки и не заменяет их.
- При запросе согласованной сводки используем один SQL-запрос либо явно выбранный общий снимок транзакции. Балансы и суммы не должны представлять разные моменты времени в одном ответе.
- Уровень изоляции и повтор транзакций выбираем для конкретного сценария и документируем. Тестируем конкурентные изменения на настоящем PostgreSQL; Go race detector не обнаруживает нарушения бизнес-инвариантов в базе.

### Идемпотентность — обязательная часть MVP

Цель: повтор запроса после тайм-аута, повторного клика или сетевого сбоя не создаёт вторую финансовую операцию. Пример: расход сохранился, ответ потерялся, клиент повторил запрос — в базе остаётся ровно один расход.

- `POST /api/v1/transactions` требует `Idempotency-Key`. После введения механизма тот же контракт распространяем на создание счетов и фоновых заданий. Отсутствующий или некорректный ключ даёт `400`; формат и предел длины фиксируем в OpenAPI.
- Клиент создаёт случайный ключ один раз для одного намерения пользователя и сохраняет его при автоматическом или ручном повторе того же запроса. Новая самостоятельная операция получает новый ключ. Отключение кнопки в UI не заменяет серверную защиту.
- Область уникальности ключа: пользователь, операция API (метод и маршрут), ключ. Пользователь определяется сессией, а не входным JSON. Ключи разных пользователей не конфликтуют и не раскрывают чужие результаты.
- PostgreSQL хранит уникальный ключ, отпечаток нормализованного валидированного запроса, идентификатор результата, HTTP-статус, необходимые заголовки и тело первоначального успешного ответа. Порядок полей JSON не должен менять отпечаток; правила нормализации фиксируем и тестируем.
- Регистрация ключа, финансовая запись и сохранение ответа выполняются в одной SQL-транзакции. Уникальное ограничение базы обеспечивает взаимное исключение для одновременных одинаковых запросов. Запрос-конкурент после ожидания читает сохранённый результат; ожидание ограничено тайм-аутом.
- Одинаковый ключ и тот же запрос возвращают первоначальный результат без нового эффекта. Одинаковый ключ с другим содержимым возвращает `409 idempotency_key_reused`.
- Если конкурент ещё не завершился и лимит ожидания исчерпан, возвращаем документированную повторяемую ошибку `409 idempotency_in_progress` с рекомендацией повторить тот же ключ. Сбой до commit откатывает и запись, и ключ. Сбой после commit восстанавливается повтором сохранённого ответа.
- Ошибки формата и доступа не сохраняем как успешные результаты. Повторно проверяем аутентификацию и владельца перед возвратом сохранённого ответа. Внутренние ошибки не фиксируем навсегда за ключом.
- Для финансовых команд в MVP успешные ключи не удаляем автоматически: защита не должна молча исчезать по TTL. Сохраняем минимальный необходимый ответ; срок хранения и удаление вместе с пользовательскими данными определим до введения очистки. Удаление самой операции не освобождает ключ для повторного создания.
- Повтор `DELETE` не создаёт нового эффекта, хотя статус ответа может отличаться. Для `PATCH` используем явную установку значений и проверку версии; идемпотентность создания не защищает от устаревшего редактирования.
- Обязательные интеграционные тесты: последовательный повтор, параллельный повтор, другой payload с тем же ключом, одинаковый ключ у разных пользователей, rollback до commit и потеря ответа после commit. Проверяем число записей и финансовые итоги, а не только HTTP-статус.

### Безопасность

- Идентификатор пользователя берём из проверенной сессии; во всех запросах к пользовательским данным учитываем владельца. Для изоляции пишем тесты минимум с двумя пользователями, даже если первая размещённая версия предназначена для одного аккаунта.
- SQL параметризован. Клиентские DTO отделены от моделей хранения: нельзя произвольно установить владельца, служебные поля или версию записи.
- Ограничиваем размер тела, длины строк, диапазоны сумм, пагинацию и время обработки; отклоняем неизвестные JSON-поля и лишние значения после JSON-документа. Ограничения на дорогостоящие операции проверяем до выполнения работы.
- Пароли хешируем Argon2id с индивидуальной случайной солью и параметрами, выбранными по актуальным рекомендациям и измерениям на целевой машине. Сессионные токены генерируем криптографически стойко, в хранилище держим их хеши, задаём срок действия и отзыв.
- Для браузера: HTTPS, HttpOnly/Secure-cookie, подходящий SameSite, защита от CSRF и явный список разрешённых origins. CORS не заменяет авторизацию. Ограничение попыток входа и нейтральные ошибки не раскрывают существование аккаунта.
- Приложение использует отдельную роль PostgreSQL без superuser и без прав изменения схемы; миграции запускаются отдельной ролью. Пользователь из учебного `POSTGRES_USER` пока является bootstrap-администратором, его не считаем готовой production-конфигурацией.
- До хранения реальных данных третьих лиц описываем экспорт и полное удаление данных пользователя, включая сессии и идемпотентные ключи.
- Секреты не коммитим и не пишем в логи. Дамп базы, реальные операции и персональные данные не попадают в публичное демо или тестовые фикстуры.
- Добавляем краткую модель угроз: доступ к чужим данным, повтор команды, конфликт изменений, утечка сессии, злоупотребление импортом и ошибочные настройки развёртывания. Проверки привязаны к этим угрозам.

### Качество кода, CI и эксплуатация

- Короткие функции с одной ответственностью, явные зависимости, предметные имена, ошибки с контекстом и проверка через `errors.Is/As`. Комментарии объясняют нетривиальные причины. Не логируем одну ошибку на каждом уровне стека.
- `context.Context` проходит от запроса к SQL и сетевым вызовам; контексты не храним в структурах. У фоновых задач свой жизненный цикл, а не отменённый контекст HTTP-запроса.
- Настройки валидируются при старте; пул соединений имеет осмысленные лимиты. Добавляем HTTP-тайм-ауты и корректную остановку: прекратить приём новых запросов, дождаться текущих в пределах срока, затем закрыть зависимости. `defer` сам по себе не заменяет обработку сигнала остановки.
- Структурированные логи через `slog`: request ID, маршрут, статус, длительность; без паролей и содержимого финансовых комментариев. Паники на HTTP-границе преобразуются в безопасный ответ и фиксируются в журнале.
- CI с первой законченной функциональностью: форматирование, `go vet`, сборка, unit-тесты, интеграционные тесты с PostgreSQL и `go test -race` в поддерживаемом Linux-окружении. Добавляем `govulncheck` и фиксируем версии инструментов; не требуем произвольный процент покрытия вместо проверки важных сценариев.
- Интеграционные тесты используют настоящий PostgreSQL той же мажорной версии, что и в production: локально и в CI — через testcontainers или сервис-контейнер CI. Каждый тест работает в изолированной базе или схеме.
- Миграции проверяются на пустой базе и на предыдущей схеме. Изменённую применённую миграцию не переписываем; для изменений добавляем новую. Применение в production — отдельный управляемый шаг, не гонка нескольких экземпляров API.
- OpenAPI отражает реальные ошибки, ограничения, авторизацию, версии и идемпотентность. Изменения контракта проверяются вместе с кодом и не ломают клиентов молча.
- README описывает воспроизводимый запуск, конфигурацию, команды проверки и текущие ограничения. ADR документируют существенные решения: SQL-модель, транзакции, идемпотентность, брокер, кэш и выделение сервиса.
- Развёртывание MVP: Docker-образ API, reverse proxy с автоматическим TLS (например, Caddy), PostgreSQL на том же сервере, ротация логов. Резервные копии хранятся вне сервера с базой.
- Метрики (`/metrics`) откладываем до инженерного этапа C; в MVP достаточно структурированных логов и `/ready`.
- Перед размещением проверяем восстановление резервной копии. Для портфолио добавляем измерения нагрузки с указанием оборудования, размера данных, сценария, конкурентности, p50/p95/p99 и доли ошибок. Не заявляем неизмеренную производительность.

## Этапы реализации

### 1. Основа и первый расход

Пользователь создаёт Go-модуль, HTTP-сервер, `/health`, подключение к базе и первую миграцию. Добавляет тестовый счёт и готовые категории, затем создание расхода и получение истории.

Первую таблицу проектируем с учётом владельца и SQL-ограничений. Срез счетов проходит через HTTP → прикладной сервис → PostgreSQL. Вместе с ним появляются интеграционные тесты и CI. До подключения создания операций к реальному клиенту реализуем контракт `Idempotency-Key`.

Ассистент создаёт визуальную основу React-сайта, историю и форму операции. До появления API использует демоданные, затем подключает рабочие запросы.

Результат: расход, добавленный на сайте, сохраняется в базе и остаётся после перезапуска сервера.

### 2. Полный учёт доходов и расходов

Добавляем доходы, редактирование и удаление, управление счетами, расчёт балансов, фильтры и пагинацию. Ассистент подключает соответствующие интерфейсы к готовым методам API.

Результат: пользователь может вести обычный ежедневный учёт и исправлять записи.

### 3. Переводы и сводка

Добавляем переводы, итоги месяца и распределение расходов по категориям. Завершаем экран обзора.

Результат: движение денег между своими счетами не искажает статистику доходов и расходов.

### 4. Готовность к личному использованию

Доводим регистрацию, вход и сессии, изоляцию данных, обработку ошибок, адаптивность и необходимые проверки. Сценарии авторизации начинаем сразу после базовых API счетов и операций; этот пункт описывает готовность к размещению, а не обязательный порядок разработки. Настраиваем HTTPS, миграции при развёртывании и ежедневную резервную копию базы с проверкой восстановления.

Результат: веб-MVP можно использовать с реальными данными на своём сервере.

### 5. Flutter после веб-MVP

Переносим основные сценарии на мобильный клиент: вход, обзор, история, операции и счета. Способ авторизации мобильного клиента согласовываем отдельно, не предполагая автоматического переноса браузерных cookie-сценариев. Бизнес-правила и финансовые расчёты остаются в Go API.

## Проверка готовности MVP

- Можно создать счета и внести начальные остатки.
- Доходы, расходы и переводы создаются, редактируются и удаляются; после перезагрузки данные сохраняются.
- Балансы корректны после изменения суммы, даты и счетов операции, а также после удаления.
- Перевод не меняет общий баланс и не попадает в доходы или расходы.
- Месячная статистика корректна на границах месяцев и при пустых данных.
- Фильтры и пагинация работают совместно; при одинаковых датах страницы не дублируют и не теряют записи.
- Изменение или удаление операции архивного счёта отвергается с `409`, баланс архивного счёта остаётся нулевым.
- Дата позже допуска или раньше нижней границы отвергается сервером.
- Невалидные суммы, несовместимые категории и переводы на тот же счёт отвергаются сервером.
- Повтор и параллельная отправка одной команды с одинаковым ключом создают одну операцию; повтор после потери ответа возвращает первоначальный результат.
- Конкурентные изменения не нарушают правила архивации и переводов; устаревшая версия редактирования даёт конфликт.
- Проверены регистрация и конфликт нормализованного email, одинаковая ошибка неверных данных входа, изоляция двух пользователей, абсолютный и неактивный сроки сессии, отзыв и повторный logout. Старые пользователи без учётных данных не могут войти. Публичная регистрация остаётся выключенной до готовности почтовых сценариев.
- Основные сценарии удобны на телефоне и компьютере.
- Сбой сохранения не стирает заполненную форму и не показывает ложный успех.
- Резервная копия успешно восстановлена в отдельную тестовую базу.
- Пользователь может неделю вести реальные расходы без необходимости исправлять данные напрямую в базе.

Для Go пишем небольшие тесты финансовых правил и интеграционные проверки сохранения и изоляции данных. Для сайта проверяем основные пользовательские сценарии, в том числе ошибки API. Объём проверок увеличиваем вместе с функциональностью.

## После MVP

Пользовательские категории, бюджеты, цели накоплений, регулярные операции, уведомления, экспорт и импорт, мультивалютность, банковские интеграции, чеки, совместный доступ, инвестиции, офлайн-режим и тёмная тема. Приоритеты определяем после использования первой версии.

### Инженерный этап A: фоновые задачи, RabbitMQ и конкурентность

Первый сценарий — экспорт истории в CSV: HTTP создаёт задание и отвечает `202` с его ID; пользователь проверяет состояние и получает готовый файл. У задания есть владелец, лимиты, срок хранения результата и состояния `pending/running/succeeded/failed`. Повтор создания задания защищён `Idempotency-Key`. Затем добавляем импорт с предварительной валидацией, отчётом об ошибках и явно описанной атомарностью импорта.

- API сохраняет задание и событие outbox в одной транзакции PostgreSQL. Outbox — таблица событий, ожидающих отправки; так commit в базе и недоступность брокера не теряют задание.
- Relay читает outbox и публикует в RabbitMQ с подтверждениями издателю, постоянными сообщениями и устойчивой очередью. Проверяем отсутствие маршрута к очереди; одно подтверждение брокера не означает, что работа выполнена.
- Доставка допускает повторы. Worker подтверждает сообщение после фиксации результата. Повтор с тем же ID не создаёт второй результат; уникальность результата и состояние задания обеспечиваются PostgreSQL. Проверяем сбой между commit результата и отправкой acknowledgement.
- У worker есть ограниченное число goroutine, лимит неподтверждённых сообщений, отмена через context, ограниченные повторы с задержкой и отдельная очередь окончательно неуспешных сообщений. Зависшее задание восстанавливается по lease/тайм-ауту владения, а не навсегда остаётся `running`.
- Файл экспорта записывается под устойчивым идентификатором задания; повтор не создаёт произвольные копии. Для внешних побочных эффектов отдельно определяем механизм идемпотентности. Гарантию exactly-once для произвольной внешней системы не обещаем.
- Рабочие goroutine принадлежат жизненному циклу worker, ошибки собираются явно, конкурентность ограничивается размером пула базы и доступными ресурсами. Изучаем `errgroup`, mutex и каналы там, где они нужны. Goroutine не равна отдельному системному потоку.
- Проверки: дубли сообщений, перезапуск worker в середине работы, недоступность брокера, исчерпание повторов, отмена и переполнение очереди. Наблюдаем длину очереди, задержку outbox, длительность заданий и ошибки.

RabbitMQ выбран для очереди работ. В MVP его не запускаем; этап начинается после стабильного финансового ядра. Модель подтверждений и повторной доставки описана в [документации RabbitMQ](https://www.rabbitmq.com/docs/reliability).

### Инженерный этап B: Redis

- Первый сценарий — общее ограничение частоты запросов для нескольких экземпляров API: атомарное обновление счётчиков, TTL, тесты параллельных запросов. Для входа при отказе общего лимитера выбираем явную безопасную деградацию: локальный ограничитель и временный отказ при превышении его лимита. Не открываем вход без ограничений молча.
- Второй сценарий, после измерений — кэш производных отчётов. Определяем допустимую задержку обновления, TTL, изоляцию ключей по пользователю и способ инвалидации. Проверяем гонку «старое чтение → изменение данных → запись старого результата в кэш»; один `DEL` после записи не решает её полностью.
- Финансовые команды, идемпотентные ключи и актуальные балансы остаются в PostgreSQL. Если отчёт требует строгой актуальности, читаем его из базы. Недоступность кэша не должна терять финансовые записи; fallback ограничиваем, чтобы не перегрузить базу.
- Кэш принимается только при измеренном выигрыше, с метриками hit/miss и тестами устаревания. Ориентир по паттерну: [Redis cache-aside](https://redis.io/docs/latest/develop/use-cases/cache-aside/).

### Инженерный этап C: отдельный сервис отчётов и gRPC

Выделяем reporting только после появления отдельной нагрузки отчётов и измерений. REST остаётся внешним API для React и Flutter. gRPC используется между backend-процессами: API запрашивает готовый отчёт у reporting через версионированный protobuf-контракт. Долгую генерацию не держим в синхронном RPC — она остаётся фоновой задачей.

- Reporting владеет своей производной моделью чтения; не пишет в таблицы финансового ядра. Сначала допускается отдельная схема и роль в той же PostgreSQL-инсталляции. При обновлении через события документируем eventual consistency и показываем время актуальности отчёта.
- `.proto` и генерируемый код имеют воспроизводимую генерацию; номера удалённых полей резервируются. CI проверяет совместимость контракта.
- RPC имеют deadlines, отмену, согласованные коды ошибок и аутентификацию сервиса. При сетевом развёртывании используем TLS. Идентификатор пользователя передаётся доверенным сервисом после внешней авторизации и проверяется принимающей стороной.
- Повторы разрешены только для безопасных или идемпотентных вызовов и ограничены общим бюджетом времени. Проверяем недоступность reporting: основной учёт продолжает работать, отчёты возвращают явную ошибку или последнее допустимое состояние.
- Добавляем OpenTelemetry для трассы HTTP → RPC → SQL, метрики задержек и ошибок без персональных данных и ID пользователей в метках метрик.

По умолчанию gRPC не задаёт deadline автоматически; задаём его явно согласно [руководству gRPC](https://grpc.io/docs/guides/deadlines/).

### Инженерный этап D: Kafka — дополнительный сценарий потоковой аналитики

Kafka не дублирует очередь экспортов RabbitMQ. Отдельная цель — поток событий изменения операций, несколько независимых потребителей и восстановление аналитической проекции повторным чтением истории. Этот этап необязателен для готового продукта и выполняется после предыдущих.

- До реализации фиксируем ADR с причиной выбора Kafka, стоимостью эксплуатации и сравнением с уже работающим RabbitMQ.
- Событие содержит ID, версию схемы, владельца, ID сущности, её версию и минимальные необходимые данные. Обрабатываем создание, изменение и удаление; не отправляем личные комментарии без необходимости.
- Выбираем ключ партиционирования по требуемому порядку, например владельцу; не предполагаем глобального порядка. Relay обязан сохранять выбранный порядок изменений, одной настройки ключа Kafka недостаточно.
- Consumer groups, offsets, дедупликация, версии сущностей и повторное проигрывание проверяются тестами. Запись результата в PostgreSQL и commit offset не являются одной атомарной транзакцией: повтор не должен удваивать проекцию.
- Replay восстанавливает тот же отчёт, включая исправления и удаления. Срок хранения событий ограничивает доступную историю; для полной перестройки описываем снимок и последующий replay. Kafka retention не заменяет удаление персональных данных и резервную копию базы.

Возможность долговременного хранения и повторной обработки потоков описана во [введении Apache Kafka](https://kafka.apache.org/intro/).

## Как подтверждаем качество проекта для портфолио

В README перечисляем только реализованные функции. Архитектурная схема соответствует запущенным процессам. Для каждого сложного механизма есть объяснение решения, негативный тест и воспроизводимый пример: повтор HTTP-команды, конфликт версии, сбой worker, отказ Redis или replay событий.

Минимальная готовность к демонстрации: рабочий финансовый сценарий, авторизация и тесты изоляции, идемпотентность, зелёный CI, миграции, описание запуска и измерения на синтетических данных. RabbitMQ, Redis, gRPC и Kafka добавляются в список освоенных технологий после выполнения соответствующих сценариев и проверок, а не после добавления зависимостей.

Race detector используем для обнаружения гонок в исполняемых тестами путях; его успешный запуск не доказывает отсутствие всех гонок. См. [документацию Go](https://go.dev/doc/articles/race_detector). Параметры хранения паролей сверяем с [OWASP Password Storage](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) перед реализацией.
